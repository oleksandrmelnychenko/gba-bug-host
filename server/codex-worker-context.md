# GBA: постійний контекст для coding worker

Це живий продукт із двома основними контурами:

- GBA Console: `gba_console` + `gba-server`;
- Ecommerce: `gba_ecommerce` + `gba-ecommerce-api`;
- джерела синхронізації: дві 1С — Fenix та AMG;
- Elasticsearch і AI-сервіси є похідними від основних синхронізованих даних.

## Незмінні інженерні правила

- Жодних коментарів у коді: ні в нових, ні в змінених рядках (пояснення — у summary/rootCause, не в коді).
- Застосунок і QA читають лише БД GBA (ConcordDb_V5 і похідні). 1С — тільки джерело для синхронізації, лише читання; застосунок, тести й перевірки ніколи не звертаються до 1С наживо.
- Дані живуть у двох світах — AMG і Fenix: ціни, націнки, документи й контурні пари розрізняються за світом. Не змішуй їх і перевіряй, в якому світі сценарій.
- Клієнти з 1С мають ієрархію: «папки»/групи (source folders) — це структура, а не клієнти. Пошуки, пікери й звіти мають повертати реальних клієнтів, а не синтетичні папки.
- Обгортка rtk скорочує/спотворює вивід git і grep: для точного виводу використовуй `rtk proxy git ...` та `/usr/bin/grep`.
- DEV API — лише через read-only проксі з промпту (GET/HEAD, авторизацію підставляє проксі); ніяких токенів, логінів і mutation-запитів.

- Виправлення має бути фул-стековим: перевір контракт API, серверну реалізацію, UI та дані.
- Не маскуй відсутні або суперечливі дані нулями, вигаданими значеннями чи мовчазним fallback.
- Гроші звіряй до копійки, кількості — одиниця в одиницю, товар — за стабільним source/net ID.
- Для дат завжди перевіряй timezone `Europe/Kyiv`, дату й час окремо, межі `from/to` та inclusive/exclusive семантику.
- Курси валют мають історичну дату. Жива ціна використовує чинний курс; документ після фіксації використовує FX snapshot.
- Фінансові CRUD-и мають бути атомарними, ідемпотентними й перераховувати похідні баланси в тій самій транзакції.
- Синхронізація має бути повторюваною та source-safe: повторний прогін не створює дублікати й не губить рухи.
- 1С є джерелом фактів, але її довідники брудні. Не об’єднуй клієнтів лише за ЄДРПОУ, телефоном або схожою назвою; зберігай source-ID, ролі та ієрархію, а неоднозначність маркуй.
- Рух товару охоплює приходи, продажі, повернення, переміщення й списання; залишок повинен випливати з повного руху.
- Пошукові індекси, storefront і AI-флот перебудовуються лише з валідного основного стану після синхронізації.
- Не запускай reset, масові мутації даних або production-операції з coding worker.
- Не клади ключі, connection strings та інші secrets у код, Git, summary або постійний контекст.

## Доказ завершення

- Спочатку перетвори опис, URL і вкладення на acceptance-критерії та перевір точний етап workflow. Екран створення, post-create логістичний шлях, перегляд і редагування не взаємозамінні.
- Для console-поведінки звіряй read-only legacy `gba_client`, якщо він доступний, але ніколи його не змінюй. Для кожного legacy/current джерела фіксуй конкретний файл або символ і те, що він доводить.
- Спочатку відтвори дефект наживо на DEV через read-only DEV API proxy (лише GET; авторизацію підставляє проксі), а якщо дефект суто візуальний — через API-дані цього екрана. Потім доведи точну причину.
- Кожна задача закінчується machine-checkable live spec `.qa-desk/verify/<TASK>.json`: GET-запити з assertions на статуси, кількості й поля сценарію. Release-worker проганяє його проти DEV після deploy і лише тоді ставить «Готовий до ретесту»; провал повертає задачу тобі.
- `needs_review`/`blocked` — лише з конкретним блокером (що недоступно, дослівна помилка, що потрібно для продовження).
- Додай регресійний тест на помилковий сценарій і позитивний тест на очікувану поведінку.
- Запусти доступні перевірки кожного зміненого репозиторію.
- Перед `fixed` переглянь повний diff кожного worktree та прибери сторонні зміни. Не редагуй глобальні test/build-конфіги лише для зеленого unrelated suite.
- `fixed` означає, що код, перевірки й live spec завершені. Release вважається підтвердженим лише після гейта, merge, deploy і зеленого live spec на DEV.
- Останні підтверджені release-и автоматично додаються нижче системою; незмерджені висновки туди не потрапляють.
